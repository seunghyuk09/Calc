# 데일리킷 계정·동기화 서버 설계서

작성일 2026-09-17 · 대상 저장소 `seunghyuk09/Calc` · 현재 커밋 `a7b8ef2`

요청 내용: *"서버를 만들고 회원가입과 로그인, 아이디 비밀번호 찾기까지 하고, 계정마다 설정이나
일정을 저장해 놓고, 다른 기기에서 로그인하면 원하는 인터페이스 그대로 쓰게 하고 싶다.
보안쪽으로도 구글플레이에 적합하도록."*

이 문서는 **플랫폼을 고르기 전에** 무엇이 필요한지를 정리합니다. 계정을 만들거나 돈을 쓰기 전에
읽고 판단하시라고 쓴 것입니다. 이 문서만으로는 아무것도 배포되지 않습니다.

---

## 0. 먼저 짚을 것 — 요청에 깔린 전제 6개

지시를 그대로 실행하기 전에, 전제부터 검증했습니다. 네 개는 수정이 필요하고 두 개는
요청에 없던 비용입니다.

### 0-1. "아이디 찾기" 는 만들 기능이 아닙니다

이메일을 아이디로 쓰면 아이디 찾기는 **존재할 수 없는 기능**입니다. 찾아 주려면 이름이나
전화번호 같은 다른 식별자를 받아 놓고 "이 사람의 이메일은 ○○○@…입니다" 라고 알려 줘야 하는데,
그건 개인정보를 더 모으고 그걸 아무에게나 흘리는 통로를 새로 파는 일입니다.

별도 아이디(예: `hyuk09`)를 두는 방식도 가능하지만, 그러면 **이메일과 아이디를 둘 다 관리**하고
아이디 중복 검사·금칙어·변경 정책이 전부 따라옵니다. 얻는 것은 "이메일을 안 외워도 된다" 하나입니다.

> **권고**: 이메일 = 아이디. 아이디 찾기는 만들지 않습니다. 화면에는 "가입한 이메일이 기억나지
> 않으시면 비밀번호 재설정을 시도해 보세요" 정도만 둡니다. 이 결정으로 화면 1개, 엔드포인트 1개,
> 그리고 개인정보 항목 1개(이름 또는 전화번호)가 통째로 사라집니다.

### 0-2. 목표의 절반은 이미 코드에 있습니다

`public/js/modules/settings.js:137` 에 **백업 내보내기 / 가져오기**가 이미 있습니다.
`exportAll()` 이 `daily-kit:` 로 시작하는 키를 전부 JSON 으로 뽑고, `ai.apiKey` 는 빼고 저장합니다
(`settings.js:140`). 앱에서는 파일 내려받기가 안 될 수 있어 본문을 화면에 펼쳐 복사까지 지원합니다.

즉 **"다른 기기에서 내 인터페이스 그대로"** 는 지금도 됩니다. 수동이라서 불편할 뿐입니다.
서버가 실제로 사는 값은 **"수동을 자동으로"** 이 하나이고, 그 대가가 이 문서의 나머지 전부입니다.

이게 요청을 깎으려는 말이 아닙니다. 비교 기준을 정확히 잡자는 것입니다.
비교는 *"아무것도 안 됨 vs 동기화"* 가 아니라 *"수동 백업 vs 자동 동기화"* 입니다.

### 0-3. 다섯 개 배포처 중 두 곳에만 로그인이 붙습니다

| 배포처 | 로그인 | 이유 |
|---|---|---|
| 안드로이드 앱 | ○ | origin `https://localhost` |
| iOS 앱 | ○ | origin `capacitor://localhost` |
| GitHub Pages | ○ | origin `https://seunghyuk09.github.io` |
| 단일 파일 `dist/데일리킷.html` | **×** | `file://` 은 origin 이 `null` 입니다. 서버가 이걸 받으려면 `Origin: null` 을 허용해야 하는데, 그 origin 은 **세상의 모든 로컬 파일과 샌드박스 iframe** 이 똑같이 가집니다. 허용하면 CORS 방어가 사실상 없어집니다 |
| claude.ai 아티팩트 | **×** | claude.ai 도메인이고, 우리가 통제하지 않는 샌드박스입니다. 기술적 가능 여부와 무관하게 **인증 토큰을 남의 도메인에서 다루지 않습니다** |

> **권고**: 뒤 두 곳은 **로그인 없는 미리보기**로 못박습니다. 두 곳은 원래 "설치 없이 보여 주는 용도"
> 였지 실사용 기기가 아닙니다. 다만 *"기기를 바꿔도 그대로"* 의 범위가 요청하신 것보다 좁아진다는 점은
> 명확히 알고 계셔야 합니다.

### 0-4. "보안쪽으로 구글플레이에 적합" — 플레이가 요구하는 건 보안이 아닙니다

정책 문서를 확인했습니다. 계정 기능이 있는 앱에 플레이가 요구하는 건 **암호화 수준이 아니라 다음 4개**입니다.

1. **계정 삭제 경로 2개** — 앱 안의 경로 **그리고** 웹 링크. 둘 다입니다 (2024-04-15 전면 시행)
2. **Data safety 양식** — 무엇을 수집하고 어디로 보내는지 신고
3. **개인정보처리방침 URL**
4. **App access** — 심사자가 쓸 테스트 계정. 영문, 상시 유효, 지역 무관, 재사용 가능

보안 설계(§7)는 이것과 **별개로** 필요합니다. 플레이가 요구해서가 아니라, 남의 비밀번호를
받아 두는 순간 필요해지는 것입니다. 두 가지를 섞어 생각하면 "심사 통과 = 안전" 이라는
틀린 결론이 납니다.

덧붙여, targetSdk 36 요건(2026-08-31 기한)은 `android/variables.gradle` 에서
`targetSdkVersion = 36` 으로 **이미 충족**되어 있습니다.

### 0-5. 요청에 없던 의존성 — 메일 발송 업체

회원가입 인증도, 비밀번호 재설정도 **메일이 나가야 성립**합니다. 그런데 이건 백엔드 무료 요금제에
포함되지 않습니다. Supabase 내장 메일은 **시간당 2통 + 팀 주소로만 발송**이라 실사용이 아예 불가능하고,
커스텀 SMTP 를 붙여도 초기 상한이 시간당 30통입니다. Cloudflare 는 메일 기능 자체가 없습니다.

즉 실제 구성은 **백엔드 + 메일 업체 + 도메인** 세 개입니다. 도메인을 사시겠다고 하신 건
이 때문에도 맞는 선택입니다 — 메일 업체는 보통 발송 도메인 인증(SPF/DKIM)을 요구합니다.

### 0-6. 법적 지위가 바뀝니다

지금 데일리킷은 서버에 아무것도 없습니다. 유출될 것이 없으므로 유출 사고도 없습니다.
로그인을 붙이는 순간 **개인정보(이메일, 비밀번호 해시, 할 일 내용, 메모 내용)를 보관하는 주체**가 됩니다.
개인 프로젝트라고 면제되지 않습니다.

여기서 생기는 실무 부담은 최소한 이 정도입니다.

- 개인정보처리방침을 실제 처리 내용과 맞게 유지
- 계정 삭제 요청 처리 (플레이 요구이면서 동시에 법적 요구)
- 유출 시 통지 의무
- 백업·보존 기간 정책

구체적인 국내 법령 적용 범위는 제가 단정할 수 없습니다. **이 항목은 직접 확인하셔야 합니다.**
다만 "서버를 켜면 책임이 따라온다" 는 사실 자체는 설계 단계에서 값을 매겨야 할 비용입니다.

## 1. 현재 상태 — 저장소에서 확인한 사실

추정이 아니라 코드에서 뽑은 값입니다.

### 1-1. 저장 키 24개

`localStorage` 에 `daily-kit:` 접두어로 저장되는 키가 **24개**입니다.
(`public/js/lib/store.js:6` 의 `PREFIX`)

```
ai.apiKey      ai.model       banner.items   cal.folded     cal.view
calc.history   memo.drawing   memo.items     quote.items    time.alarm
time.lastPreset               todo.categories               todo.dayView
todo.items     todo.lastCategory             todo.view      todo.weekBase
ui.czOpen      ui.lang        ui.lastSeen    ui.prefs       ui.theme
update.lastCheck              weather.place
```

`daily-kit:sw-purged` 는 `sessionStorage` 라 동기화 대상이 아닙니다 (`update.js:133`).

### 1-2. 항목 모양

```js
// todo.js:962 — 할 일
{ id, text, done, scope, period, category, time?, at, doneAt }

// memo.js:381 — 메모
{ id, text, at }

// quote.js:73 — 글귀
{ id, text, author, at }
```

**셋 다 `at`(만든 시각)만 있고 `updatedAt` 이 없습니다.** 삭제 흔적(tombstone)도 없습니다.
이게 동기화의 가장 큰 구조적 걸림돌입니다 (§3).

### 1-3. 용량 폭탄 — `memo.drawing`

낙서판은 캔버스를 통째로 PNG data URL 로 저장합니다 (`memo.js:439`).
현재 상한은 **4,000,000자 ≈ 4MB** 이고, 넘으면 저장을 거부합니다 (`memo.js:441`).

계정당 4MB 를 그대로 올리면 Supabase 무료 DB 500MB 기준 **최악의 경우 125계정**에서 찹니다.
텍스트 데이터 전부를 합친 것보다 그림 하나가 큽니다.

### 1-4. CSP 가 없습니다

`public/index.html` 에 `Content-Security-Policy` 가 **없습니다**. 지금은 XSS 가 나도 잃을 게
내 메모뿐이지만, 로그인을 붙이면 **XSS 하나가 계정 탈취**가 됩니다. §7-3 에서 다룹니다.

### 1-5. origin 판정 로직이 이미 있습니다

`update.js` 의 `isNativeUrl()` 이 정답을 이미 갖고 있습니다. CORS 허용 목록을 여기서 그대로 가져옵니다.

```js
if (loc.port) return false;                  // 개발 서버에는 포트가 있습니다
if (loc.protocol === 'capacitor:') return true;
return loc.protocol === 'https:' && loc.hostname === 'localhost';
```

### 판단이 갈리는 것 — 미리 정하고 가야 합니다

- **`memo.drawing`**: 올리려면 DB 가 아니라 오브젝트 스토리지로 가야 하고, 그러면 업로드/다운로드
  경로와 용량 정책이 따로 필요합니다. **1단계 제외**를 권합니다. 대신 "그림은 이 기기에만 저장됩니다"
  를 화면에 명시합니다.
- **`time.alarm`**: 알람은 *그 기기에서 울리는* 것입니다. 폰에서 맞춘 알람이 태블릿에서도 울리는 게
  맞는지는 제품 결정입니다. 저는 **동기화 제외**를 권합니다. 동기화하면 "안 맞춘 알람이 울린다" 는
  버그 신고가 나옵니다.
- **`banner.items`**: 사용자가 편집한 배너 내용이면 A급이 맞습니다.

## 3. 데이터 모델 마이그레이션 — 서버보다 먼저 해야 할 일

**현재 항목 구조로는 정확한 동기화가 불가능합니다.** 이유는 두 가지입니다.

### 3-1. `updatedAt` 이 없습니다

`at` 은 만든 시각이라 절대 안 바뀝니다. 할 일을 체크하거나 글을 고쳐도 `at` 은 그대로입니다.
그래서 **"어느 쪽이 더 최신인가" 를 판단할 근거가 없습니다.**

### 3-2. 삭제 흔적이 없습니다

폰에서 할 일을 지우면 배열에서 빠질 뿐입니다. 서버는 "지웠다" 와 "아직 못 받았다" 를
구분할 수 없습니다. 이 상태로 병합하면 **지운 항목이 부활합니다.** 동기화 앱에서 가장 흔하고
가장 짜증나는 버그입니다.

### 3-3. 목표 구조

```js
// 할 일
{
  id, text, done, scope, period, category, time?,
  at,                    // 만든 시각 (기존 그대로)
  doneAt,                // 기존 그대로
  updatedAt,             // 추가: 마지막으로 고친 시각
  deletedAt: null,       // 추가: 지운 시각. null 이 아니면 삭제된 항목
}
```

삭제는 배열에서 빼지 않고 `deletedAt` 을 찍습니다. 화면에서는 `deletedAt` 이 있는 항목을
거릅니다. 서버와 맞춘 지 30일 지난 tombstone 은 양쪽에서 정리합니다.

### 3-4. 기존 데이터 이관

이미 기기에 쌓인 항목에는 두 필드가 없습니다. 읽어 올 때 채웁니다.

```js
// updatedAt 이 없는 예전 항목은 만든 시각을 그대로 씁니다.
// 실제보다 오래된 값이지만, 이후 수정부터는 정확해집니다.
const migrated = { ...item, updatedAt: item.updatedAt ?? item.at, deletedAt: item.deletedAt ?? null };
```

> **중요**: 이 마이그레이션은 **서버 없이 지금 할 수 있고, 서버를 안 만들기로 해도 손해가 없습니다.**
> 그래서 §8 의 1단계에 넣었습니다. 서버 결정을 미루셔도 이건 먼저 해 두는 게 맞습니다.

## 4. 동기화 규칙

### 4-1. 오프라인 우선

**인터넷이 없어도 앱은 지금과 똑같이 동작해야 합니다.** 데일리킷은 계산기·타이머·메모가 핵심이고,
그건 네트워크와 무관합니다. 로그인 때문에 비행기 모드에서 앱이 멈추면 개악입니다.

- 모든 쓰기는 **localStorage 에 먼저** 합니다 (지금과 동일)
- 동기화는 **그다음에, 실패해도 되는 작업**으로 돕니다
- 로그인하지 않은 사용자는 지금과 **완전히 동일한 앱**을 씁니다

### 4-2. 동기화 시점

- 앱을 켤 때 1회
- 앱으로 돌아올 때 (`visibilitychange`) — 단, 최소 간격 60초
- 쓰기 후 디바운스 (예: 5초)
- 설정 탭의 수동 "지금 동기화" 버튼

### 4-3. 항목 병합 규칙 (B급)

`id` 를 기준으로 짝을 맞추고, 짝마다 이렇게 판정합니다.

| 상황 | 결과 |
|---|---|
| 한쪽에만 있음 | 그대로 받아들임 |
| 양쪽에 있고 `updatedAt` 이 다름 | **늦은 쪽이 이김** |
| 양쪽에 있고 `updatedAt` 이 같음 | 서버 것을 채택 (임의 기준이지만 일관됨) |
| 한쪽에 `deletedAt` 이 있음 | **삭제가 이김** (단, 반대쪽 `updatedAt` 이 `deletedAt` 보다 늦으면 살림) |

"삭제가 이긴다" 를 기본으로 잡은 이유: 지운 게 되살아나는 것보다 **살아 있어야 할 게 지워지는
쪽을 사용자가 더 빨리 알아챕니다.** 되살아난 항목은 "내가 지웠나?" 하고 넘어갑니다.

### 4-4. 시계를 믿지 않습니다

`updatedAt` 은 기기 시계입니다. 기기 시계는 틀립니다 — 시간대 변경, 수동 조정, 배터리 방전.
이미 `session.js` 에서 같은 문제를 겪고 방어해 뒀습니다.

> **규칙**: 서버는 받은 `updatedAt` 을 그대로 쓰되, **서버 수신 시각을 함께 기록**합니다.
> 기기 시계가 미래로 몇 년 가 있는 등 명백히 이상한 값은 서버 시각으로 고정합니다.
> 커서(`?since=`)는 **서버 시각 기준**으로 발급합니다. 기기 시계로 커서를 만들면 시계가 틀린
> 기기 하나가 자기 데이터를 영원히 못 받습니다.

### 4-5. 충돌을 사용자에게 묻지 않습니다

할 일 앱에서 "어느 쪽을 쓰시겠습니까?" 팝업은 실패한 설계입니다. 규칙으로 자동 해결하고,
혹시 잘못돼도 **기존 백업 기능(`exportAll`)이 마지막 안전망**입니다. 동기화를 켜기 전에
자동 백업을 한 부 만들어 두는 것을 1단계에 넣었습니다.

|---|---|---|
| 회원가입 | ○ | 이메일 + 비밀번호. 인증 메일 발송 |
| 메일 인증 | ○ | 링크 클릭. **웹 페이지가 필요합니다** (앱만으로는 안 됨) |
| 로그인 | ○ | |

| 비밀번호 재설정 | ○ | 메일 링크. **웹 페이지 필요** |
| 아이디 찾기 | **×** | §0-1 |

메일 링크는 결국 **웹 페이지 3개**(인증 완료, 비밀번호 재설정, 계정 삭제 요청)를 요구합니다.
GitHub Pages 에 정적으로 올릴 수 있지만, 도메인을 사시면 그쪽에 두는 편이 깔끔합니다.

### 5-2. 엔드포인트

```
POST   /auth/signup            { email, password }      → 202  (응답은 항상 동일)
POST   /auth/verify            { token }                → 200
POST   /auth/login             { email, password }      → { access, refresh }
POST   /auth/refresh           { refresh }              → { access, refresh }   회전
POST   /auth/logout            { refresh }              → 204
POST   /auth/password/forgot   { email }                → 202  (응답은 항상 동일)
POST   /auth/password/reset    { token, password }      → 200  (전체 refresh 무효화)
GET    /me                                              → { email, createdAt }
DELETE /me                     { password }             → 204
GET    /sync?since=<cursor>                             → { settings, items, tombstones, cursor }
POST   /sync                   { settings, items, tombstones } → { cursor }
```

### 5-3. 응답을 항상 같게 하는 이유

`/auth/signup` 과 `/auth/password/forgot` 은 **이메일이 있든 없든 똑같이 202** 를 돌려줘야 합니다.
"이미 가입된 이메일입니다" 나 "가입되지 않은 이메일입니다" 는 **계정 존재 여부를 알려 주는 조회 API**
입니다. 이걸로 특정 이메일이 이 서비스에 가입했는지를 아무나 확인할 수 있게 됩니다.

대신 메일 내용을 다르게 보냅니다. 이미 가입된 주소에는 "이미 계정이 있습니다. 비밀번호를
잊으셨나요?" 를 보냅니다. 이러면 진짜 소유자만 정보를 받습니다.

### 5-4. 토큰

| 항목 | 값 | 이유 |
|---|---|---|
| access 수명 | 15분 | 탈취돼도 창이 짧습니다 |
| refresh 수명 | 30일 | 매번 로그인시키면 안 씁니다 |
| refresh 회전 | **필수** | 쓸 때마다 새로 발급하고 옛것은 폐기 |
| 재사용 감지 | 폐기된 refresh 가 오면 **그 계정 전체 세션 무효화** | 탈취 흔적입니다 |

## 6. 보안 설계

플레이 요구(§0-4)와 **별개**입니다. 비밀번호를 받아 두면 필요한 것들입니다.

### 6-1. 비밀번호

- 해시: **Argon2id** 우선. 불가한 런타임이면 고반복 PBKDF2 또는 bcrypt
- 최소 길이 8자 이상, **복잡도 규칙은 두지 않습니다** (길이가 더 중요합니다)
- 유출 목록 대조(Have I Been Pwned k-anonymity)는 선택. 붙이면 좋지만 필수는 아닙니다

> **주의**: Cloudflare Workers 같은 런타임에서 Argon2 를 돌릴 수 있는지, CPU 시간 제한에 걸리지
> 않는지는 **제가 확인하지 못했습니다.** 플랫폼을 고르시면 그때 실제로 돌려 보고 확정해야 합니다.
> 이건 플랫폼 선택을 뒤집을 수 있는 항목입니다.

### 6-2. 전송

- HTTPS 전용, HSTS
- CORS 허용 목록은 **정확히 3개**. 저장소의 `isNativeUrl()` 과 일치시킵니다

```
https://seunghyuk09.github.io     (GitHub Pages)
https://localhost                 (안드로이드 Capacitor WebView)
capacitor://localhost             (iOS Capacitor WebView)
```

`Origin: null` 은 **허용하지 않습니다** (§0-3).

### 6-3. CSP — 로그인보다 먼저

지금 `index.html` 에 CSP 가 없습니다. 이 상태로 토큰을 들이면 **XSS 한 방이 계정 탈취**가 됩니다.

`connect-src` 는 코드에서 `fetch` 로 실제 호출하는 곳을 전수조사해 채웠습니다.

| 호스트 | 쓰는 곳 |
|---|---|
| `api.anthropic.com` | `ai.js:12` |
| `api.github.com` | `update.js:19` (업데이트 확인) |
| `api.open-meteo.com` | `weather.js:9` (예보) |
| `geocoding-api.open-meteo.com` | `weather.js:10` (지역 검색) |

```
default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:;
connect-src 'self' https://api.<도메인> https://api.anthropic.com https://api.github.com https://api.open-meteo.com https://geocoding-api.open-meteo.com;
frame-ancestors 'none';
base-uri 'self';
```

`github.com`(APK 내려받기, `update.js:20`), `www.google.com` · `search.naver.com` ·
`www.perplexity.ai`(`ai.js:187-189` 외부 검색 링크)는 **fetch 가 아니라 링크 이동**이라
`connect-src` 에 넣지 않습니다. 넣으면 안 되는 걸 넣은 것이고, 빠뜨리면 검색 버튼이 죽습니다.

`form-action` 은 넣지 않았습니다. 이 앱에는 `<form>` 제출이 없지만, `'none'` 으로 잠가 두면
나중에 폼을 하나 추가했을 때 이유 모르게 막힙니다.

> **위험 고지**: CSP 를 켜면 **지금 잘 도는 기능이 조용히 깨질 수 있습니다.** 인라인 스크립트,
> 인라인 이벤트 핸들러, `data:` 이미지, 낙서판의 `blob:` 이 전부 걸립니다.
> **먼저 `Content-Security-Policy-Report-Only` 로 켜서 위반을 모은 뒤** 실제 적용하는 순서가
> 맞습니다. 이건 서버 작업과 무관하게 독립적으로 할 수 있습니다.
>
> 위 목록을 처음 쓸 때 저도 `geocoding-api.open-meteo.com` 을 빠뜨렸습니다. 그대로 적용했으면
> **날씨 탭의 지역 검색만 조용히 죽었을 것**입니다. 이 종류의 실수는 눈으로 읽어서는 안 잡힙니다.

### 6-4. 기기에 토큰을 어디 둘 것인가

| 방법 | 장점 | 단점 |
|---|---|---|
| `localStorage` | 지금 구조 그대로, 추가 의존성 0 | **XSS 한 방에 통째로 털립니다** |
| Capacitor Preferences (네이티브 저장소) | 웹 JS 에서 직접 못 읽음 | 네이티브 플러그인 추가 = 지금 잘 도는 안드로이드/iOS 빌드에 변경 위험 |

> **권고**: refresh 토큰만 네이티브 저장소로, access 토큰은 **메모리에만**(새로고침하면 사라짐).
> 다만 플러그인 추가는 실제로 APK 를 빌드해서 확인해야 합니다. 현재 빌드는 안정적으로 돌고 있고,
> 여기 손대는 건 별도 PR 로 분리해야 합니다.

**전부 직접 짭니다** — 비밀번호 해싱, 토큰 회전과 재사용 감지, 메일 발송 연동, 레이트 리밋,
계정 존재 여부 은닉까지. 이건 이 프로젝트 전체에서 **틀렸을 때 가장 비싼 코드**이고,
틀려도 테스트가 통과합니다. 버그가 나면 남의 계정이 털립니다.

Supabase 를 고르면 그 코드를 안 짭니다. 대신 특정 업체에 묶이고, 7일 일시정지를 피하려면
사실상 월 $25 입니다.

> - Cloudflare Workers $5 + Resend 무료 = **월 $5** + 인증 코드를 직접 짜는 노동과 위험
> - Resend 무료는 **월 3,000통 / 하루 100통 / 도메인 1개**. 개인 앱 규모에서는 충분합니다

이 컨테이너의 외부 통신은 프록시로 제한돼 있습니다. GitHub Pages 는 정적 호스팅이라

## 11. 아직 확인하지 못한 것

정직하게 남깁니다. 설계를 뒤집을 수 있는 항목들입니다.

1. **Cloudflare Workers 에서 Argon2 실행 가능 여부** (§6-1) — CPU 시간 제한에 걸릴 수 있습니다
2. **Capacitor Preferences 플러그인 추가가 현재 안드로이드/iOS 빌드를 깨는지** (§6-4)
3. **CSP 적용 시 실제로 깨지는 기능의 범위** (§6-3) — Report-Only 로 측정해야 압니다
4. **claude.ai 아티팩트 샌드박스의 네트워크 정책** — §0-3 은 기술적 가능 여부가 아니라
   "남의 도메인에서 토큰을 다루지 않는다" 는 원칙으로 판단한 것입니다
